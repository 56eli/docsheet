## 3. Findings (ranked)

### 🔴 P1 — CSP hash blocks the no-flash dark-mode script

**File:** `docs/index.html` (lines 8 and 22–31)

The Content-Security-Policy `script-src` whitelists a hash:

```
'sha256-u2/u4gxax738T0FZixKekRcJpSj2LbWauC5THe95guI='
```

The actual inline script computes to:

```
sha256-qULmN/IfgO0KcdvNpANXyfZHBIgYfm4o368jeDomJJY=
```

I computed the latter directly from the file bytes between `<script>` and
`</script>`. They do not match. Under a strict CSP (`default-src 'self'`, no
`'unsafe-inline'` for scripts), the browser **refuses to execute the inline
pre-paint dark-mode script**. Consequence: users with dark-mode preference see a
flash of the light theme before `app.js` boots and applies the class. The dark mode
still works once `app.js` loads (it is same-origin, so not CSP-blocked), but the
"no flash" guarantee the audit docs claim is broken.

The deep-audit doc explicitly claims "hash verified matches inline dark-mode
script" — that claim is stale; the script or the hash was edited without
re-syncing. There is **no automated test** that recomputes the hash, which is why
this drifted silently.

**Fix:** recompute the hash from the current script and update the CSP meta tag
(or add a test that asserts the two match). One-line change.

without re-deriving from the master URLs. Adding the mirror `--check` to CI (and
to the test `SCRIPTS` list) closes that gap.

### 🟠 P2 — Filename-proposal format drift on master UUID 221

**Files:** `data/research_master_draft.csv`, `data/filename_proposal_YYYYMM.csv`

Master row **221** ("Progressive Levels of Consciousness — A Special Talk Presented
in Oxford (2003)") has:

- `format = streaming` in the master draft
- `format = ` (blank) in `data/filename_proposal_YYYYMM.csv`

Every other master row has matching `format` values across the two files. The
filename itself (`2003 - Progressive Levels … Oxford.mp4`) is still unique and
valid, so the build passes — but the proposal's `format` column is the grouping
key for the v4.1 carrier-suffix collision rule, and a blank there means a future
regeneration could mis-group this row. The proposal is treated as a hand-maintained
input (the builder only *applies* it, never regenerates it), so this needs a
one-cell correction: set UUID 221's `format` to `streaming`.

The master counts confirm the asymmetry: 22 `streaming` rows in master vs 21 in
the proposal.

### 🟡 P3 — `lecture_series_review.csv` is stale relative to its generator

Regenerating `lecture_series_review.csv` from `generate_lecture_review.py`
produces a 330-line diff. The committed copy was hand-curated after bootstrap
(it retains `proposed_month` values like "08" that the generator leaves blank),
and `NEXT_AGENT_HANDOFF.md` §5 explicitly notes these two CSVs are
"hand-maintained after bootstrap generation … regenerating them over the
committed copies intentionally produces diffs (title fixes, month '08' vs ''),
that is normal, not damage."

So this is **documented as expected**, not a defect — but it means there is no
automated way to tell *intentional* hand edits from *accidental* drift in this
file. The test suite treats it as a sandbox input only (determinism is tested in
a fresh copy, not against the committed file). Worth a one-line note in the CSV's
companion `.md` clarifying that the committed version is the reviewed snapshot and
the generator is a bootstrap tool, not a rebuild command.
